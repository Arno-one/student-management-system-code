# 从零实现一个带"记忆"的多轮对话系统

> 一个学生管理系统的 AI 作业模块里，我设计了一套两层记忆架构的对话功能。这篇文章记录从需求分析到落地的完整思路。

## 背景

这个模块的需求很简单：学生可以和 AI 助教自由对话，AI 需要记住上下文。类似 ChatGPT 那样，换个会话就是一段新对话，关了页面再打开还能接着聊。

但拆开来看，有几个有意思的问题：

- 对话记录存在哪里？内存还是数据库？
- 历史消息越多上下文越长，Token 会不会爆炸？
- 多个用户之间怎么隔离？
- 能不能让 AI 自己总结对话主题，方便用户回溯？

下面按我实际的实现顺序来展开。

---

## 数据模型：两张表解决持久化

我把对话拆成两个概念——**会话**和**消息**，用两张 MySQL 表来承载。

**talk_session —— 会话表**

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | INT PK | 自增主键 |
| `user_id` | VARCHAR(100) | 用户标识，用来隔离不同用户的对话 |
| `session_title` | VARCHAR(200) | 首条消息的前 30 字自动作为标题 |
| `summary` | TEXT | 对话主题摘要，由 DeepSeek 每轮自动归纳 |
| `style` | VARCHAR(100) | 用户沟通风格偏好，同上自动识别 |
| `is_deleted` | TINYINT | 逻辑删除标记 |
| `create_time` | DATETIME | 创建时间 |
| `update_time` | DATETIME | 有新消息时自动更新，作为排序依据 |

**talk_message —— 消息表**

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | INT PK | 自增主键 |
| `session_id` | INT FK | 外键关联 talk_session.id，级联删除 |
| `role` | VARCHAR(20) | system / user / assistant |
| `user_content` | TEXT | 用户的问题 |
| `ai_content` | TEXT | 大模型的回复 |
| `create_time` | DATETIME | 创建时间 |

这里把 `role` 区分成三种，`system` 消息只存用户不可见的人设提示词（比如"你是一个经验丰富的工作助手"）。用户和 AI 的对话分开存进 `user_content` 和 `ai_content`，方便后续做数据分析或者导出。

---

## 记忆架构：短期 + 长期两层

如果每次对话都从数据库读全部历史消息再发给大模型，有俩问题：

1. **慢**——每轮都查一次库、拼一次上下文，响应延迟明显。
2. **贵**——对话越长，Token 消耗越快，上下文窗口迟早爆掉。

所以我把记忆拆成两层：

### 短期记忆（内存缓存）

```python
_session_cache: dict[int, dict] = {}
# key = session_id
# value = {"summary": "...", "style": "...", "messages": [...]}
```

- 用户打开历史会话 → 从数据库把消息加载进内存，之后的读写全走缓存。
- 服务重启缓存清空 → 用户下次打开会话时自动从数据库恢复，对用户几乎无感。

### 长期记忆（数据库持久化）

- 每轮对话同步写入 `talk_message`，数据不会丢。
- 起到**兜底**和**回溯**的作用——就算服务器重启了，所有历史对话还在。

### 上下文窗口控制

对话消息数量不受限制地增长的话，早晚超出模型上下文上限。我定的规则是：

> 最近 10 条对话消息全部发送；超出部分用 summary 替代。

也就是说发给大模型的 messages 结构大致是：

```json
[
  {"role": "system", "content": "基础人设 + 对话背景 + 用户偏好"},
  {"role": "user", "content": "倒数第10条用户发言"},
  {"role": "assistant", "content": "倒数第10条AI回复"},
  ...
  {"role": "user", "content": "本轮用户输入"}
]
```

10 条对话大概在 2000-4000 token 左右，加上 system prompt 和 summary 的背景信息，整体控制在一个比较合理的范围里。

## 自动摘要与风格识别

这是我觉得最有意思的部分：让 AI 自己总结自己在聊什么。

每轮对话结束后，我会额外调一次 DeepSeek，prompt 非常简单：

```
你是一个对话分析助手。根据用户和大模型的最新一轮对话，
更新对话主题摘要和用户沟通风格偏好。
输出一个 JSON，格式固定为：
{"summary": "简短的主题摘要（≤50字）",
 "style": "偏好的沟通风格关键词（如：简洁/详细/幽默/严肃/技术型等，≤20字）"}
只输出 JSON，不要多余内容。
```

模型返回的 JSON 解析后，同时更新内存缓存和数据库。下次对话时，summary 和 style 会拼进 system prompt：

```
你是一个经验丰富的工作助手，会帮助我完成一些任务
【对话背景】用户在咨询 Python 异步编程相关问题
【用户偏好】技术型、详细
```

这样大模型在回复时会自动调整语气和详略程度——比硬编码一套 system prompt 灵活很多。

style 不在前端展示，它只作为背景信息发给大模型。summary 则展示在会话列表里，用户翻历史记录时一眼就能看出这轮聊了什么。

## 用户隔离

user_id 是整个系统的隔离边界：

- 每次创建会话都绑定 user_id。
- API 层每个接口都校验 `session.user_id == user_id`，不匹配就返回 403。
- 前端进入对话页面前，强制输入用户 ID 并确认，确认态存 localStorage，刷新不用重新输。

```
┌──────────────────────────────────────┐
│  前端登录门禁                          │
│  "请输入你的用户ID" → [确认并进入对话]   │
└──────────────┬───────────────────────┘
               │ 确认后
┌──────────────┴───────────────────────┐
│  对话界面                              │
│  [用户: arno] [切换]  [+ 新建会话]      │
│  ┌──────────┬──────────────────────┐  │
│  │ 历史会话   │  消息气泡区域         │  │
│  │ · 异步编程 │  ┌──────────────┐    │  │
│  │   技术型   │  │ 用户消息      │    │  │
│  │ · 请假邮件 │  ├──────────────┤    │  │
│  │   简洁型   │  │ AI 回复       │    │  │
│  │           │  └──────────────┘    │  │
│  └──────────┴──────────────────────┘  │
│  [输入框________________] [发送] [清空] │
└──────────────────────────────────────┘
```

## API 设计

全部走 RESTful 风格，返回统一结构 `{code, msg, data, total}`：

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/work/talks/sessions?user_id=` | 获取用户所有未删除会话，按更新时间倒序 |
| `POST` | `/work/talks/sessions` | 创建新会话，body: `{user_id, title}` |
| `DELETE` | `/work/talks/sessions/{id}?user_id=` | 逻辑删除（is_deleted=1） |
| `GET` | `/work/talks/{id}/messages` | 获取会话全部消息，按时间正序 |
| `POST` | `/work/talks` | 发送消息，body: `{session_id, user_id, prompt}` |
| `POST` | `/work/talks/clear?session_id=&user_id=` | 清空消息（物理删除，保留会话壳） |

POST `/work/talks` 是这个模块的核心接口，流程图如下：

```
用户发送消息
    │
    ▼
校验会话归属（user_id 是否匹配）
    │
    ▼
内存缓存是否已加载？—→ 否 —→ 从数据库加载到内存
    │ 是
    ▼
拼接 messages：
  system = 基础人设 + summary + style
  + 最近10条历史对话（内存缓存）
  + 本轮用户输入
    │
    ▼
调用 DeepSeek v4  →  拿到回复
    │
    ▼
写入内存缓存（user + assistant 各一条消息）
写入数据库（持久化）
更新会话 update_time
    │
    ▼
调用 DeepSeek 归纳摘要和风格
写入内存缓存 + 数据库
    │
    ▼
返回回复给前端
```

## 代码分层

遵循项目已有的分层惯例：

| 层 | 文件 | 职责 |
|----|------|------|
| Model | `model/Talk.py` | SQLAlchemy ORM，定义两张表的字段和关联 |
| DAO | `DAO/talk_dao.py` | 数据库的增删查改，不包含业务逻辑 |
| Service | `service/work_service.py` | 核心业务：两层记忆调度、摘要生成、上下文拼接 |
| API | `API/work_api.py` | FastAPI 路由，参数校验，统一响应封装 |
| 前端 | `frontend-vue/src/views/WorkView.vue` | Vue 3 Composition API，对话 UI |
| 样式 | `frontend-vue/src/assets/styles.css` | 暗色主题，消息气泡、会话列表样式 |
| DDL | `util/talk_tables.sql` | 建表语句，可直接导入 |

## 技术栈

- **后端**：Python FastAPI + SQLAlchemy + PyMySQL
- **大模型**：DeepSeek v4 Flash（对话 + 摘要共用）
- **数据库**：MySQL
- **前端**：Vue 3 + Vite
- **API 密钥管理**：通过 `config.py` 读取 `.env`，源码零硬编码

---

## 总结

几个关键设计决策回顾：

1. **内存 + 数据库 双层记忆**——内存保证响应速度，数据库保证数据不丢，服务重启后自动恢复。
2. **上下文窗口控制**——最新 10 条消息 + summary 背景板，兼顾连贯性和 Token 成本。
3. **自动摘要**——让大模型自己归纳对话主题，前端展示摘要方便用户回溯，style 注入 system prompt 优化回复质量。
4. **用户隔离**——user_id 贯穿前后端，API 层校验归属，前端登录门禁强制确认身份。

如果需要在此基础上扩展，可以考虑的方向：流式返回（SSE）、对话导出、多模型切换、基于 summary 的对话搜索。不过那是下一篇博客的事了。
