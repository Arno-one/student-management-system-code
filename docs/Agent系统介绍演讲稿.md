# 学生管理系统 Agent 子系统介绍演讲稿

---

## 开场：这个项目到底做了什么

各位好，今天我汇报的是学生管理系统里的 Agent 智能体子系统。

如果用一句话概括，这个项目不是“在系统里加了一个聊天框”，而是**在一个传统学生管理系统上，落地了一套可控、可扩展、可观测的 Agent 工程体系。**

从 v1.0 MVP 到 v2.3，我们完成了四轮迭代，最终交付了：

- 11 类意图识别能力
- 8 个业务工具
- 3 个角色 Persona
- 3 类结构化卡片
- 1 套 HITL 人工确认机制
- 1 个 MCP 地图能力底座
- 1 个 Supervisor 多 Agent 最小闭环
- 以及配套的反馈闭环、监控面板和 UI 自动化回归护栏

我今天重点讲四件事：**为什么要这样做、我们是怎么做的、最终做成了什么、以及这套系统为什么能继续演进。**

---

## 第一部分：为什么做

二阶段需求文档给了我们一个很明确的目标：**把原本偏管理型的学生管理系统，升级成一个具备知识问答、角色互动、业务查询和智能陪伴能力的 AI 产品。**

但这里有一个前提不能变：我们面对的不是一个新项目，而是一个已经存在的一阶段系统。它已经有学生管理、成绩管理、班级管理、就业管理、NL2SQL 和 RAG 等模块，所以 Agent 的接入不能推翻重来，也不能破坏现有业务。

也就是说，这个项目真正的难点，不是“把 AI 做出来”，而是**把 AI 以工程化方式嫁接进现有系统，而且还要保证稳定、可控、可维护。**

所以我们在编码前先做了一个关键决策：**不引入 LangChain 的通用 Agent 框架，而是自研一套 Planner 驱动的受控执行架构。**

原因很简单。我们的业务不是开放世界问题，而是相对确定的问题：

- 成绩查询就是查成绩工具
- 知识问答就是走 RAG 工具
- 数据统计就是走 NL2SQL 工具
- 邮件草拟就是走邮件工具

在这种场景里，让 LLM 自由选工具并不会显著提升能力，反而会带来三类风险：

- 不调用该调的工具
- 调错工具
- 重复调用同一个工具

所以我们要的不是“更像魔法”，而是“更像工程”。也就是：**每一步都可追溯、可审计、可降级，出了问题可以快速定位。**

---

## 第二部分：怎么做的

我们整套 Agent 系统，核心上坚持了四条设计原则。

**第一，局部嫁接，不重构主干。**

`agent_system/` 被设计成一个独立子系统目录，与原有 `API/`、`service/`、`DAO/` 平行存在。这样做的好处是，Agent 的迭代不会污染原业务，也不会把原有系统拖进大规模重构。

**第二，Planner 驱动，受控执行。**

系统的核心链路是：**意图分类 → 计划生成 → 执行器按计划执行**。

这里 LLM 可以参与判断和生成，但不直接掌控底层工具调用。它负责“理解”，不直接负责“拍板执行”。真正执行时，系统走的是结构化计划和确定性工具链。

**第三，现有能力先包装成工具，再进入 Agent 体系。**

我们没有让 Agent 跨层直接调用 DAO、RAG 或零散业务模块，而是统一包装成工具，比如：

- `score_tool`
- `rag_tool`
- `nl2sql_tool`
- `weather_tool`
- `email_tool`
- `commute_plan_tool`
- `nearby_service_tool`

每个工具都遵循统一输入输出规范，Executor 只处理标准化结果，而不关心工具内部细节。

**第四，Persona 只影响回复风格，不影响意图分类。**

这一点很关键。我们把“怎么说”和“做什么”严格拆开：

- 意图分类只看任务本身
- Persona 只在最终回复阶段注入

所以无论是学业导师、陪伴班主任，还是“昕哥”，都不会影响底层工具路由。这让角色扩展变得非常轻，也保证了系统行为的稳定性。

## 第三部分：v2.0 做的最关键重构

v1.0 MVP 先把知识问答、多轮对话、学业导师和基础工具链跑通了。到了 v2.0，需求一下子多了起来：天气、邮件、HITL、多角色、输入安全中间件、独立数据表，都要接进来。

这个时候如果继续沿用 MVP 阶段那种“每个工具各写各的、Executor 用 `if/elif` 硬编码分发”的方式，系统很快会失控。

所以 v2.0 的核心工作不是简单加功能，而是**先把底层框架统一掉**。

我们做了三件事：

**第一，抽出 BaseTool 和 ToolContext。**

所有工具统一继承 BaseTool，只需要实现 `run(ctx, params)`。数据库会话、用户信息、角色、会话 ID 等运行时依赖，统一由 ToolContext 提供。

**第二，重写 Executor。**

原来工具分发是一长串 `if/elif`，重构后变成查表调用：

`_TOOL_REGISTRY[step.tool_name].run(ctx, params)`

这一步看起来只是代码写法变了，但它的价值非常大。因为从这之后，新增工具只需要：

- 实现一个新工具类
- 在注册表里加一行
- 在 Planner 里补一条兜底计划

Executor 核心逻辑不用改。

**第三，扩展 PlanStep，支持链式工具协作。**

我们给 PlanStep 增加了 `params` 和 `inputs_from` 字段，让工具之间可以自动传值。比如天气查询要先 geocode 再查天气，邮件草拟可以复用通勤规划结果，这些都不需要手写流程胶水，而是由 schema 驱动的链式执行来完成。

这一步实际上为后面的天气、通勤、周边服务、Supervisor 多 Agent 协作都打好了底座。

## 第四部分：安全体系是怎么建立起来的

在 Agent 系统里，安全不是一个补丁，而是从 v2.0 就开始设计进去的。

我们做了三层防护。

**第一层，输入中间件管线。**

整个链路是：

`input_guard → query_rewriter → policy_checker`

它分别负责：

- 拦截提示注入、敏感操作、超长输入
- 结合最近历史做指代消解和问题改写
- 对改写后的文本做最终安全核验

它的输出不是模糊的，而是明确的三种结果：

- pass：直接放行
- rewrite：改写后放行
- reject：拒绝进入后续链路

**第二层，HITL 人工确认机制。**

邮件发送是第一个高风险操作。Agent 可以帮助用户生成邮件内容，也可以预填收件人和主题，但真正发出去之前必须停下来，交给用户确认。

前端会展示一个可编辑的邮件预览面板，用户确认之后才发送。到了 v2.1，这套机制从“邮件专用逻辑”升级为按 `tool_name` 配置的轻量规则系统，后续新增高风险工具时可以直接复用。

**第三层，邮件白名单。**

这个设计很朴素，但很重要。它保证即使受到提示注入，Agent 也不能向任意地址乱发邮件。

到了 v2.3，我们又把这套 HITL 机制跑通到了 Supervisor 多 Agent 场景里，让第二步邮件确认能够正确识别 `step_id`，说明这套安全管线不只是单工具可用，而是跨 Agent 场景也能成立。

## 第五部分：为什么 v2.1 是“从能用到可运营”的分水岭

v2.0 之后，Agent 已经能工作了，但还缺一个关键问题的答案：**它到底好不好用，哪里好，哪里不好？**

所以 v2.1 的重点，不再是“再加一个功能”，而是建立运营闭环。

我们主要做了四件事。

**第一，反馈闭环。**

每次 Agent 回复都会生成一个任务记录，前端给出点赞和点踩入口，点踩可以补充原因，后端保证同一任务不重复提交。这样，Agent 的好坏第一次被结构化记录下来。

**第二，监控面板。**

管理员可以看到：

- 调用量
- 成功率
- 平均耗时和 P99
- 意图分布
- 工具失败排行
- 待确认数量
- 最近任务详情
- 差评原因聚合

也就是说，我们不再只是“感觉这个 Agent 还行”，而是能基于数据回答：**哪些意图最常用、哪些工具最不稳定、用户为什么不满意。**

**第三，MCP 地图能力底座。**

我们没有把天气能力写成一个孤立模块，而是接入腾讯地图 MCP，并封装了通用客户端。这样天气、通勤、周边服务后面都能复用同一套地图能力底座。

更重要的是，MCP 不可用时工具会自动降级到 REST，这保证了系统不是“依赖新能力才能活”，而是“优先用新能力，出问题还能退回去”。

**第四，天气卡片系统。**

这一步让 Agent 回复不再只是文本。天气结果会以结构化卡片形式通过 SSE 下发，前端用 `WeatherCard` 组件渲染。这个机制后来发展成通用卡片协议，为 route 和 poi_list 卡片打下了基础。

## 第六部分：v2.2 做的是底层能力升级

v2.2 不是最“炫”的版本，但它是非常关键的一版，因为它补的是系统长期可用的基础能力。

**第一，记忆压缩。**

如果把所有历史对话都无脑塞给 LLM，上下文迟早会爆。于是我们把记忆拆成了：

- 会话摘要
- 最近 5 条原文

摘要负责让模型知道“之前聊到了哪里”，最近原文负责保留当前话题的细节。这样既能延长多轮对话能力，又不会让上下文无限膨胀。

**第二，通勤规划。**

基于腾讯地图 MCP，我们封装了 `commute_plan_tool`，支持公交、地铁、开车、步行等通勤方案。这里也不是简单调用地图接口，而是配合输入校验、中间件澄清和天气辅助提醒一起工作。

**第三，UI 自动化回归护栏。**

随着卡片、悬浮 Agent、主题样式越来越多，UI 回归开始频繁出现。于是 v2.2 建立了两层护栏：

- 静态脚本检查已知污染模式
- Playwright 驱动真浏览器做 DOM 回归

到 v2.3，这套护栏已经覆盖了 81 项静态检查和 2 个真浏览器回归场景。

---

## 第七部分：v2.3 做的不是“堆功能”，而是把系统收口

v2.3 在 v2.2 基础上继续推进了五件事。

**第一，周边生活服务推荐。**

基于地图 MCP 的地点搜索能力，落地了 `nearby_service_tool`，可以支持“学校附近有哪些医院”“公司附近哪里能吃饭”这类真实生活场景。

**第二，卡片协议收口。**

我们把卡片协议明确成字段级契约，当前落地了 `weather`、`route`、`poi_list` 三类卡片，并用 `card_version` 控制前后端独立演进。这意味着系统后续继续加结构化展示时，不需要重做前后端协作方式。

**第三，Supervisor 多 Agent 协作一期。**

这里我们没有一步冲到“大而全的多 Agent”，而是刻意收敛成一个最小闭环：

“从宝安中心到龙岗坐地铁怎么去，并写邮件通知老师。”

这个场景跨了路线规划和邮件两个领域。Supervisor 负责任务拆解和状态汇总，MapAgent 和 CommunicationAgent 分别复用现有工具链。这个最小闭环跑通之后，多 Agent 协作才真正具备可继续扩展的基础。

**第四，体验收口。**

比如：

- 悬浮 Agent 会记住用户最近选择的角色
- WorkView 的天气展示复用统一 WeatherCard
- 新增“昕哥”角色，让角色差异不只是语气轻微变化，而是真正有风格区分

**第五，监控面板增强。**

新增了 provider 分布、差评关键词聚合、任务详情弹窗等能力，管理员看到的不再只是数字，而是能顺着数据定位问题。

## 第八部分：工程质量是怎么兜住的

这套系统能一路从 v1.0 走到 v2.3，没有在中间失控，一个很重要的原因是我们始终把“工程质量”放在功能前面。

我们的基本节奏是：

- 功能实现前先明确边界和验收口径
- 功能实现后做后端编译、前端构建和针对性验证
- 每个功能都沉淀测试文档到 `docs/testing/`

到 v2.3，已经累计了 20 份测试数据文档。

同时，v2.2 开始建立 UI 自动化回归，v2.3 的最终验证结果是：

- 后端编译通过
- 前端生产构建通过
- UI 回归 81/81 通过
- Playwright 2/2 通过

这说明这套系统不是“能演示一次”，而是**具备持续迭代能力、而且迭代过程中能兜住回归风险。**

## 第九部分：最后怎么总结这套 Agent 系统

如果从能力上看，我们交付的是：

- 11 类意图识别
- 8 个业务工具
- 3 个角色 Persona
- 3 类结构化卡片
- 1 套 HITL 规则化确认机制
- 1 个 MCP 地图能力底座
- 1 个 Supervisor 多 Agent 最小闭环

如果从价值上看，我觉得更重要的是另外四点：

**第一，它是可控的。**

LLM 不直接随意调工具，系统行为可追溯、可审计、可降级。

**第二，它是安全的。**

输入有中间件，风险操作有 HITL，邮件有白名单，地图和工具结果都有限制边界。

**第三，它是可运营的。**

有 AgentTask、AgentFeedback、监控面板、差评原因聚合，系统好不好不是拍脑袋判断，而是有数据支撑。

**第四，它是可持续演进的。**

加工具不需要重写 Executor，加角色不影响意图分类，加卡片不破坏旧协议，MCP 挂了有 REST 兜底，LLM 失败了有兜底计划。

---

## 结尾

回头看这个项目，我认为它最重要的意义，不是“功能做了多少”，而是**把 Agent 从一个演示型能力，做成了一套可以真正落在现有系统里的工程化子系统。**

它不是一个“演示完就结束”的 Demo，而是一套：

- 能持续迭代
- 能治理风险
- 能被观测
- 能被运维和优化

的 Agent 工程体系。
