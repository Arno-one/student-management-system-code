# 学生管理系统（二阶段）需求文档

## 一、项目背景

一阶段项目的核心目标，是围绕“学生管理系统”完成明确的业务功能点开发，重点在于：

- 学生信息管理
- 成绩管理
- 班级管理
- 就业管理
- 权限与系统管理
- 基础 AI 能力接入（如 NL2SQL、RAG、智能录入等）

一阶段的特点是：

- 功能范围明确
- 实现路径相对固定
- 更强调“按需求完成模块”

二阶段项目的目标则不同。  
二阶段不再只是“把已有需求实现出来”，而是要求在现有系统基础上，加入更多 **AI 产品化思维**，提升系统的：

- 智能交互能力
- 角色化体验
- 主动服务能力
- 场景延展能力

因此，二阶段项目的核心思路是：

**在现有学生管理系统的业务主干上，引入“知识问答机器人 + 角色化 Agent”双线能力，把系统从传统管理系统升级成智能学生管理系统。**

---

## 二、项目目标

本阶段项目希望实现以下目标：

1. 在学生管理系统中新增一个“知识问答机器人”，锻炼 RAG 能力。
2. 在学生管理系统中新增一个“角色化 Agent”，提升产品趣味性和交互深度。
3. 让 AI 不只是“会聊天”，而是能结合系统已有数据和业务能力，完成实际任务。
4. 保持现有业务系统稳定，不破坏一阶段已完成的主要功能。
5. 形成完整的项目交付材料，包括需求、表设计、接口设计、开发计划等。

---

## 三、产品定位

本项目二阶段的产品定位为：

**一个既能管理学生数据、又能提供智能问答、学业辅导、情绪陪伴和业务查询能力的智能学生管理系统。**

系统不再只是面向管理员的“管理后台”，而是向更强的“智能服务平台”升级。

---

## 四、目标用户

本项目主要面向以下几类用户：

### 1. 学生

主要需求：

- 查询成绩
- 询问课程、制度、考试等问题
- 获得学习建议
- 在压力或烦恼场景下获得基础陪伴与安慰

### 2. 教师 / 班主任

主要需求：

- 查询学生表现
- 了解班级整体情况
- 查看统计分析结果
- 借助 AI 进行辅助答疑或提醒

### 3. 管理员

主要需求：

- 维护系统功能
- 管理权限和角色
- 监控 AI 模块运行情况
- 查看 Agent 使用与日志情况

---

## 五、二阶段整体方案

本阶段建议采用“双模块推进”的方式实现：

### 模块 A：知识问答机器人

定位：

- 基于 RAG 的知识问答机器人
- 面向学校制度、课程信息、系统使用说明、学习资料等内容

主要价值：

- 锻炼 RAG 检索增强能力
- 让系统具备“懂知识”的能力
- 为 Agent 提供知识基础能力

### 模块 B：角色化 Agent

定位：

- 基于学生管理系统背景设计的智能体角色
- 能结合业务数据、知识检索和人格化表达完成任务

主要价值：

- 提升系统趣味性
- 增强多轮交互体验
- 让 AI 从“回答问题”升级到“完成任务”

---

## 六、知识问答机器人需求

### 6.1 功能定位

知识问答机器人是一个基于 RAG 的问答模块，主要负责回答特定知识范围内的问题。

### 6.2 典型知识范围

可根据项目实际情况选择其一或组合：

- 学校制度知识库
- 学生手册知识库
- 考试与成绩相关规则
- 课程与作业说明
- 系统使用帮助文档
- 某一特定主题知识库

### 6.3 核心需求

1. 用户可以通过自然语言提问。
2. 系统基于知识库检索相关内容后生成回答。
3. 回答应尽量结合检索依据，减少幻觉。
4. 回答应保持语言自然、清晰、适合学生阅读。
5. 问答结果最好能展示“依据来源”或“相关片段”。

### 6.4 典型示例

- “学校请假流程是什么？”
- “补考成绩怎么算？”
- “系统里怎么查询我的作业？”
- “这篇学习资料主要讲了什么？”

### 6.5 验收重点

- 是否能检索到相关知识
- 回答是否围绕知识库内容
- 是否具备基本稳定性
- 是否有来源依据展示

---

## 七、角色化 Agent 需求

### 7.1 功能定位

角色化 Agent 不是普通聊天机器人，而是：

**具有人设、语言风格、一定情绪理解能力，并能调用系统工具完成任务的智能体。**

### 7.2 角色设计要求

项目组可围绕“学生管理系统”背景，自主设计一个或多个角色。  
推荐从以下方向中选择：

- 学业导师
- 虚拟班主任
- 成长陪伴助手
- 诗词老师 / 国风老师
- 校园顾问

### 7.3 角色设定与语言风格（Persona & Tone）

每个 Agent 需要明确以下内容：

1. 角色身份  
   例如：班主任、学业导师、温柔学姐、国风老师等

2. 说话风格  
   例如：温和、鼓励、古风、理性、亲切、共情

3. 回答边界  
   例如：
   - 不提供医疗诊断
   - 不做危险建议
   - 不做越权操作
   - 涉及敏感问题时提醒联系老师或家长

### 7.4 学业辅导与诗词鉴赏（Academic Assistant）

建议将该方向作为 Agent 的主能力之一。

具体要求：

- 能回答学习相关问题
- 能对学生成绩表现做基础分析
- 能给出适度的学习建议
- 能加入诗词鉴赏、文学表达等趣味功能

典型示例：

- “我最近数学成绩下降了，应该怎么办？”
- “帮我分析一下我这学期成绩的变化。”
- “请用古风一点的方式鼓励我准备考试。”
- “帮我赏析一下‘长风破浪会有时’这句诗。”

### 7.5 情绪疏导与心理陪伴（Emotional Companion）

该方向是二阶段项目的重要亮点，但必须控制边界。

#### 需求描述

针对学生在成长中的烦恼，如：

- 考试压力
- 人际矛盾
- 学习焦虑
- 自我怀疑

提供具有基本共情能力的温和回应。

#### 具体要求

1. **共情逻辑**

- 不直接给出冷冰冰的解决方案
- 先表达理解和接纳
- 再给出温和建议

例如：

> “想来你心中定是委屈的……”

2. **敏感捕捉**

- 能识别明显负面情绪
- 能在合适时机主动表达关心

3. **边界约束**

- 不做心理诊断
- 不替代专业心理咨询
- 对严重敏感内容应做风险提示，并建议联系老师、家长或专业人员

### 7.6 调用工具能力

Agent 不应只是闲聊，还应具备调用系统已有能力的功能。

最典型的需求是：

#### 学生想查询成绩

要求：

- Agent 能识别“查询成绩”意图
- 调用系统已有成绩查询工具
- 将结果用自然语言组织返回给用户

除成绩查询外，还可扩展：

- 查询学生基本信息
- 查询班级情况
- 查询就业信息
- 查询统计结果
- 调用 NL2SQL 完成自然语言问数
- 调用 RAG 完成知识型问答

### 7.7 多轮对话能力

建议 Agent 支持基础多轮上下文，包括：

- 记住当前对话主题
- 支持追问
- 避免每轮都从零开始理解

例如：

用户：

> “帮我查一下我的成绩。”

下一轮：

> “那数学这门课怎么样？”

系统应能理解“这门课”与前文有关。

## 八、推荐功能组合方案

结合项目现状，推荐采用以下组合方案：

### 方案一：知识问答机器人 + 学业导师 Agent

特点：

- 最稳妥
- 最容易与现有系统融合
- 最容易做出完整闭环

适合：

- 时间有限
- 希望兼顾业务价值和 AI 展示效果

### 方案二：知识问答机器人 + 班主任陪伴 Agent

特点：

- 产品感更强
- 角色化更明显
- 更容易体现共情与互动

适合：

- 想突出“陪伴型 AI”特色
- 有时间做风格打磨和风险边界控制

### 方案三：知识问答机器人 + 多能力综合 Agent

特点：

- 技术含量高
- 能串联问答、问数、业务查询、陪伴

适合：

- 小组能力较强
- 有足够时间进行测试和收敛

本项目推荐优先采用：

**方案一：知识问答机器人 + 学业导师 Agent**

原因：

- 更容易落地
- 更容易复用现有模块
- 更符合“学生管理系统”主题
- 更适合作为二阶段主展示能力

## 九、功能范围说明

### 9.1 本阶段必须完成

1. 一个可运行的知识问答机器人
2. 一个角色化 Agent
3. 至少一个可调用工具的场景
4. 基础多轮对话能力
5. 基本文档交付

### 9.2 本阶段推荐完成

1. 成绩查询工具接入
2. 学业分析建议
3. 诗词鉴赏或人格化表达
4. 情绪共情能力
5. 问答来源展示

### 9.3 本阶段可选扩展

1. 更多角色设定
2. 任务历史记录
3. 用户反馈机制
4. Agent 偏好记忆
5. 风险动作人工确认
6. 更细粒度的日志与监控

---

## 十、非功能需求

### 10.1 稳定性

- 不影响现有学生管理系统主业务流程
- 新增 AI 模块出错时，不应导致整个系统不可用

### 10.2 可维护性

- 新增 AI 模块需保持清晰结构
- 尽量避免把 Agent 逻辑直接堆进原有业务文件

### 10.3 可扩展性

- 后续应支持增加更多角色或更多工具
- 应支持继续扩展知识库范围

### 10.4 安全性

- 涉及业务数据时要遵守权限约束
- 情绪陪伴类功能要控制回答边界
- 高风险动作不应无条件自动执行

### 10.5 用户体验

- 回答要自然、可读
- 查询结果要清楚
- 风格要符合设定角色

---

## 十一、与现有项目的关系

二阶段项目是在一阶段项目基础上的增强，而不是推翻重做。

因此：

- 原有 `API / service / DAO / model / scheme` 主结构保留
- 原有学生、成绩、班级、就业、统计等模块继续复用
- 原有 `RAG` 模块可作为知识问答能力基础
- 原有 `NL2SQL` 模块可作为 Agent 的问数工具能力

二阶段新增内容应优先采用“局部接入”的方式实现，即：

**在现有项目中新增 AI/Agent 子系统，而不是全面重构整个工程。**

- 用户反馈表

建议至少覆盖：

- 聊天接口

- 反馈接口

- 开发分期

- 时间安排
- 风险点

## 十三、开发分期建议

### P1：知识问答机器人

目标：

- 搭建 RAG 问答入口
- 实现知识检索与回答
- 支持基本前后端联调

### P2：学业导师 Agent

目标：

- 加入角色设定
- 加入成绩查询工具调用
- 加入学习建议输出

### P3：陪伴与多轮能力增强

目标：

- 加入基础情绪共情能力
- 加入对话上下文记忆
- 增强交互体验

### P4：扩展与优化（可选）

目标：

- 增加更多角色
- 增强日志与反馈
- 增加风格切换与个性化能力

---

## 十四、验收标准建议

项目验收时，建议重点关注以下方面：

### 1. 功能完整性

- 是否实现知识问答机器人
- 是否实现角色化 Agent
- 是否至少完成一个工具调用场景

### 2. AI 能力体现

- 是否真正使用了 RAG
- 是否体现了 Agent 的角色设定和语言风格
- 是否体现了多轮、工具、记忆等能力中的至少一部分

### 3. 产品思维体现

- 是否不是简单“加一个聊天框”
- 是否围绕学生管理场景做了合理设计
- 是否体现了自主构思能力

### 4. 工程实现质量

- 是否保持原系统稳定
- 是否结构清晰
- 是否有配套文档

---

## 十五、一句话总结

二阶段项目的核心，不是单纯再做几个功能，而是：

**让原本偏管理型的学生管理系统，进化成一个具备知识问答、角色互动、业务查询和智能陪伴能力的 AI 产品。**
