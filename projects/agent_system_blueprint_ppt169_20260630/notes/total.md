# 01_封面

各位老师好，今天汇报的不是一个会聊天的功能，而是一套嵌入学生管理系统的 Agent 工程化子系统。它从 v1.0 MVP 演进到 v2.3，核心变化是从单点能力走向可控、可扩展、可观测、可回归的长期运行体系。

---

# 02_交付总览

先给结论：当前交付已经从功能点升级为工程能力矩阵。系统沉淀了 11 类意图、8 个业务工具、3 个 Persona、3 类结构化卡片，并且有验收、测试和回归证据支撑这些能力不是孤立演示。

---

# 03_工程价值公式

这套 Agent 的价值不只看功能数量，而要看四个可验证维度：可控、可扩展、可观测、可回归。Planner、Executor 和 HITL 提供控制力，BaseTool 和卡片协议提供扩展力，AgentTask 与反馈面板提供观测力，UI 回归和 Playwright 提供回归能力。

---

# 04_架构蓝图

架构上最重要的判断，是把 `agent_system` 做成独立子系统，而不是侵入原有学生、成绩、班级和就业模块。这样 Agent 能持续迭代，但原业务主干仍保持边界清晰，降低了后续改造的风险。

---

# 05_受控执行链

系统没有让大模型自由拍板调用工具，而是让意图分类、计划生成和注册表驱动执行。这样做的目的，是把“不调用、调错、重复调用”这三类风险收敛到确定链路里，让每一步都可以追踪和降级。

---

# 06_RAG工程链

RAG 也不是简单接入向量库，而是一条问答质量工程链。它从入库切片、混合召回、CrossEncoder 精排，到 small-to-big 上下文扩展、来源引用和资料不足拒答，都是围绕“答得准，也知道什么时候不能乱答”来设计的。

---

# 07_统一底座

v2.0 的真正转折不是新增几个工具，而是统一底座。BaseTool、ToolContext、工具注册表和 PlanStep 链式执行，让后续天气、邮件、通勤、周边服务以及 Supervisor 协作都能用同一种方式接入。

---

# 08_版本演进

从 v1.0 到 v2.3，系统经历的是一条从可运行到可运营的路线。v1.0 先跑通最小闭环，v2.0 统一底座，v2.1 建立反馈和监控，v2.2 补长期可用能力，v2.3 则把体验、监控和协作进一步收口。

---

# 09_验收结论

验收结论可以直接给出：21 项验收条目全部通过，通过率为百分之百。这里的通过不是只看演示效果，而是把必须完成、推荐完成、可选扩展和非功能要求都放进同一张证据表里核对。

---

# 10_非功能验收

非功能验收说明，这不是一次性 Demo。稳定性来自独立边界和降级策略，可维护性来自分层目录和独立模型，可扩展性来自统一工具契约，安全性来自权限、白名单和 HITL，用户体验则由流式回复、全局入口和结构化卡片共同支撑。

---

# 11_运营闭环

系统好不好用，不靠主观感觉，而要看任务、反馈、监控和健康状态。AgentTask 记录任务链路，AgentFeedback 收集用户评价，Provider、意图、工具和 MCP 健康状态让问题能从指标回到具体链路。

---

# 12_Supervisor协作

Supervisor 的价值在于证明多 Agent 协作已经跨域跑通，但它没有急着做大而全的平台。当前用路线规划加邮件通知作为最小闭环，让 Supervisor 负责拆解和汇总，MapAgent 与通信 Agent 复用已有工具，邮件发送前仍由 HITL 兜住风险。

---

# 13_交付文档

交付物不是一组截图，而是一条可以复查的证据链。需求与迭代文档说明范围，模型和接口说明系统边界，测试文档和协议规范说明能力可以被重复验证和继续扩展。

---

# 14_演示路径

现场演示建议先从用户体验进入，再切到后台治理，最后回到架构价值。这样观众先看到系统能解决什么问题，再看到为什么它不是偶然能跑通，最后理解 Planner、BaseTool、HITL 和 Supervisor 的工程意义。

---

# 15_下一步治理

当前最小闭环已经闭上，后续重点不应只是继续横向加功能，而是治理复杂度。下一阶段建议继续完善能力目录、扩展结构化卡片、沉淀可复用测试数据，并把监控面板从定位问题推进到辅助决策。

---

# 16_结尾

回到最后一句话，我们做的不是一个会聊天的功能，而是一套能在真实业务系统里长期运行、持续扩展，并且可以被管理和优化的 Agent 子系统。它已经具备长期运行、风险治理、观测运维和回归验证的工程化落地能力。
