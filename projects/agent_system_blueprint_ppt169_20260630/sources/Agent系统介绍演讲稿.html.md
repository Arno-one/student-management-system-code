> 如果让我先用工程化的视角评价这套 Agent 系统，我会先给一个结论：它最有价值的地方，不是“在学生管理系统里接了一个 AI 对话入口”，而是把 Agent 做成了一个能长期演进、能稳定落地、能持续运维的业务子系统。
>
> 它的亮点很集中。第一，它的边界清晰，`agent_system/` 以独立子系统方式接入现有主干，没有把 AI 逻辑打散到原业务代码里；第二，它的执行受控，走的是“意图识别 -> Planner 规划 -> Executor 执行”的确定性链路，不把关键动作完全交给大模型自由发挥；第三，它的能力可插拔，成绩查询、RAG、NL2SQL、天气、邮件、地图等能力都被统一封装成工具接口，后续新增能力时扩展成本很低；第四，它的质量是可运营的，HITL、监控面板、Supervisor、多级 fallback、结构化卡片协议这些能力已经说明，它考虑的不是“演示能不能跑起来”，而是“上线后能不能管得住、看得清、扩得动”。
>
> 所以这套系统真正值得讲的，不是它“会聊天”，而是它已经具备了一套工程系统该有的边界感、纪律性和演进能力。

## 一、30 秒开场版

> 各位好，今天我汇报的不是一个“会聊天的功能”，而是一套真正嵌入学生管理系统里的 Agent 子系统。
>
> 它从 v1.0 MVP 一路演进到 v2.3，最终形成了一个可控、可扩展、可观测、可回归的 Agent 工程体系。
>
> 到目前为止，我们已经交付了 11 类意图识别、8 个业务工具、3 个 Persona、3 类结构化卡片、1 套 HITL 机制、1 套 RAG 工程化检索链路、1 个地图 MCP 能力底座，以及 1 个 Supervisor 多 Agent 最小闭环。

## 二、演讲主线

### 2.1 这个项目到底做了什么

如果用一句话来概括，这个项目不是“在系统里加了一个聊天框”，而是：

**在一个传统学生管理系统上，落地了一套可控、可扩展、可观测的 Agent 工程体系。**

它解决的不是“能不能让 AI 说话”，而是另外一个更难的问题：

**怎么把 AI 以工程化方式嫁接进现有业务系统，而且还能保证稳定、可控、可维护。**

### 2.2 为什么我们没有直接上通用 Agent 框架

在设计阶段，我们做了一个关键决策：

**不直接引入 LangChain 式的开放式 Agent，而是自研 Planner 驱动、Executor 受控执行的架构。**

原因很直接。这个系统的大多数问题并不是开放世界问题，而是相对确定的问题：

- 成绩查询就是走成绩工具
- 知识问答就是走 RAG 工具
- 数据统计就是走 NL2SQL 工具
- 邮件草拟就是走邮件工具

在这种场景下，让 LLM 自由选工具并不会显著提升能力，反而会带来三种风险：

1. 不调用该调的工具
2. 调错工具
3. 重复调用同一个工具

所以我们要的不是“更像魔法”，而是“更像工程”。

### 2.3 我们是怎么把它做成工程体系的

整套系统有四个核心设计原则。

#### 第一，局部嫁接，不重构主干

`agent_system/` 被设计成一个独立子系统目录，和原有 `API/`、`service/`、`DAO/` 平行存在。

这样做的好处是：

- Agent 的迭代不会污染原业务
- 不会把原系统拖进大规模重构
- 主业务和智能能力能保持边界清晰

#### 第二，Planner 驱动，受控执行

系统的核心链路是：

`意图分类 -> 计划生成 -> 执行器按计划执行`

这里 LLM 负责“理解”和“生成计划”，但不直接拍板底层工具调用。真正执行的是结构化计划和确定性工具链。

#### 第三，现有能力先包装成工具，再进入 Agent 体系

我们没有让 Agent 跨层直接调用 DAO、RAG 或零散模块，而是统一包装成工具：

- `score_tool`
- `rag_tool`
- `nl2sql_tool`
- `weather_tool`
- `email_tool`
- `commute_plan_tool`
- `nearby_service_tool`

这样 Executor 只处理标准化结果，不关心工具内部细节，后续扩工具时成本就很低。

#### 第四，Persona 只影响“怎么说”，不影响“做什么”

这一点非常关键。

我们把“怎么说”和“做什么”严格拆开：

- 意图分类只看任务本身
- Persona 只在最终回复阶段注入

所以无论是学业导师、陪伴班主任，还是昕哥，都不会影响底层工具路由。这既保证了角色差异，也保证了系统行为稳定。

## 三、版本演进怎么讲

### 3.1 v1.0 MVP：先把最小闭环跑通

v1.0 的目标不是做大而全，而是先证明这条链路能跑通：

- 知识问答
- 多轮对话
- 学业导师 Persona
- 基础工具链
- SSE 流式返回

这个阶段最重要的成果，是把 Agent 从“概念”变成“可运行能力”。

#### v1.0 里的 RAG，不只是“接一个向量库”

知识问答看起来像是最基础的功能，但这里其实有一个很重要的设计亮点：

**我们做的不是“把文档丢进向量库然后搜索”，而是按真实问答质量去设计了一整条 RAG 检索工程链路。**

这条链路可以分成三段讲。

**第一段，检索前先把知识库治理好。**

入库时不是简单按固定长度硬切，而是根据文档类型做结构化处理：

- 四大名著按“第 X 回”保留章节边界
- Markdown 按标题切分
- PDF 按页提取后再识别中文标题、数字标题
- DOCX 优先使用标题样式
- 工程文档支持 PDF、DOCX、Markdown 多格式统一入库

切片阶段还做了 500 字左右的 chunk、50 字 overlap，并优先按段落、句号、分号、逗号这些中文语义边界切分。换句话说，它不是把知识切碎，而是尽量让每个片段仍然像一段“能回答问题的话”。

同时，入库字段也做了统一设计：`doc_id`、`text`、`question`、`answer`、`reason`、`file_name`、`chunk_index`、`source_type`、`dense_vector`。普通文档和 QA 问答对都能进入同一套检索体系，但又能通过 `source_type` 区分用途。

这里最关键的一点是：**标题会被注入正文，例如“【章节标题】正文”。** 这能明显提升召回效果，因为用户提问时常常问的是章节、主题或场景，而不一定刚好说中正文里的某一句话。

**第二段，检索中不是单路召回，而是混合召回。**

用户问题进入检索前，会先经过查询改写，把口语化问题改成关键词更密集的检索语句。比如用户说得很随意，系统会尽量保留人物、地点、工程参数、单位、时间这些关键限定。

真正检索时走的是 Milvus 混合检索：

- Dense Vector 负责语义相似
- BM25 稀疏向量负责关键词命中
- RRF 负责把两路结果融合
- QA 和原文可以通过过滤条件分阶段检索

这样做的好处是，语义相近但关键词不同的问题能搜到，关键词非常明确的参数型问题也不容易被语义模型“带偏”。

**第三段，检索后继续提升精度，而不是直接交给大模型。**

RRF 召回后，系统还接了 CrossEncoder 精排，用 `BAAI/bge-reranker-v2-m3` 对“用户问题 + 候选片段”逐对打分，再取最可信的 Top-K。

在工程文档库里，还额外做了 QA 优先策略：

- 先查标准 QA 问答对
- 如果分数和领先幅度足够高，直接返回标准答案
- 如果不够稳，再回退查原文片段
- 如果资料不足，明确回答“资料不足，无法确定”

最后进入生成阶段前，还会做 small-to-big：命中某个 chunk 后，把它前后相邻片段一起取出来，避免答案只看到半句话。同时做去重、token 预算控制和来源引用，保证回答既不超上下文，也能说明“依据来自哪里”。

所以这套 RAG 的亮点不是“用了向量库”，而是从切片、字段、入库、混合召回、精排、上下文扩展、引用生成到保守拒答，都在围绕一个目标做设计：

**让 AI 回答得更准，也让它知道什么时候不该乱答。**

这也是后面 Agent 系统能稳定扩展知识问答能力的基础。

### 3.2 v2.0：最关键的不是加功能，而是统一底座

到了 v2.0，需求开始明显变多：

- 天气
- 邮件
- HITL
- 多角色
- 输入安全中间件
- 独立任务表和反馈表

如果继续沿用 MVP 阶段“每个工具各写各的、Executor 用 `if/elif` 分发”的方式，系统很快就会失控。

所以 v2.0 做的最关键动作，是先把底层统一掉：

1. 抽出 `BaseTool` 和 `ToolContext`
2. 把 Executor 改成注册表驱动
3. 扩展 `PlanStep`，支持链式工具协作

这一步给后续天气、通勤、周边服务、Supervisor 协作都打下了底座。

### 3.3 v2.1：从“能用”走到“可运营”

v2.1 是一个非常关键的分水岭。

因为从这个版本开始，我们不再只回答“它能不能工作”，而是开始回答：

**它到底好不好用，哪里稳定，哪里不稳定，用户为什么满意或不满意。**

这个阶段我们做了四件特别重要的事：

1. 反馈闭环
2. 监控面板
3. 腾讯地图 MCP 能力底座
4. 天气卡片系统

从这里开始，Agent 已经不只是一个会回复的模块，而是开始具备运营和观测能力。

### 3.4 v2.2：补长期可用的基础能力

v2.2 看起来没那么“炫”，但它补的是特别关键的长期能力：

#### 第一，记忆压缩

我们把长对话记忆拆成：

- 会话摘要
- 最近 5 条原文

这样既能保留上下文延续性，又不会让 prompt 无限制膨胀。

#### 第二，通勤规划

基于腾讯地图 MCP 落地 `commute_plan_tool`，支持公交、地铁、驾车、步行等方案。

而且不是“地图接口直连”，而是配合：

- 输入校验
- 中间件澄清
- 天气辅助提醒

一起工作。

#### 第三，UI 自动化回归护栏

从 v2.2 开始，我们建立了两层护栏：

1. 静态脚本检查
2. Playwright 真浏览器回归

这一步的意义是，Agent 不只是“功能在长”，整个系统也开始有能力承接持续迭代。

### 3.5 v2.3：不是堆功能，而是把系统收口

v2.3 的重点，不是继续横向堆功能，而是把“能力、协议、体验、观测”一起收口。

这一版主要有六个亮点。

#### 亮点一：周边生活服务推荐

基于地图 MCP 的地点搜索能力，落地了 `nearby_service_tool`，支持真实生活场景，例如：

- 学校附近有哪些医院
- 宝安中心附近有什么吃的
- 某个商圈周边有哪些常用服务

#### 亮点二：卡片协议收口

我们把结构化结果收敛成统一卡片协议，当前落地了三类：

- `weather`
- `route`
- `poi_list`

并通过 `card_version` 控制前后端独立演进，这让后续继续增加结构化展示不会推倒重来。

#### 亮点三：Supervisor 多 Agent 一期最小闭环

我们没有一上来就做“大而全”的多 Agent，而是刻意收敛到一个最小可验证场景：

**从宝安中心到龙岗怎么走，并顺手写一封邮件通知老师。**

这个场景跨了路线规划和邮件两个领域，Supervisor 负责任务拆解与状态汇总，MapAgent 和 CommunicationAgent 分别复用现有工具链。

#### 亮点四：角色与交互体验继续收口

这一版我们让角色不只停留在“语气差异”，而是真的开始影响用户体感：

- 悬浮 Agent 记住最近一次 Persona 选择
- 新增“昕哥”角色
- 快捷工具面板前置常用能力
- Agent 欢迎语按 Persona 固定模板注入

#### 亮点五：监控能力从“能看”升级到“能定位问题”

我们把监控面板继续增强，新增了：

- provider 分布
- 差评原因聚合
- 最近任务详情速查
- 地图 MCP 健康状态

管理员不再只是看几个数字，而是能顺着数据快速定位问题。

#### 亮点六：管理端体验和性能也做了工程化收口

这是最近一轮特别值得讲的一点。

我们不是只把功能做出来，还把后台管理端体验和可运维性继续打磨了一层：

1. **Agent 监控接口聚合**
   - 前端不再并发请求多组监控接口
   - 后端新增 `/agent/admin/dashboard`
   - 由一次聚合返回总览、趋势、意图、工具、provider、差评原因和 MCP 健康状态

2. **数据库索引补齐**
   - 为 `agent_task` 的 `create_time`、`status`、`intent` 补齐索引
   - 而且不是只改模型声明，还在初始化阶段对老库自动补索引

3. **监控页首屏自动加载**
   - 进入 `Agent监控` 窗口后，默认直接展示近 7 天数据
   - 用户不需要再先手动点一次“刷新”

4. **系统管理导航体验优化**
   - 折叠态侧栏改为独立 emoji rail
   - 展开后自动定位当前模块
   - 管理员从任意页面进系统管理时，不会再丢失当前上下文

5. **启动路径瘦身和重依赖懒加载**
   - 数据库自动建表改成可配置开关，生产或演示环境可以跳过 `create_all` 和索引探测
   - 腾讯地图 MCP 改成 `eager / lazy / disabled` 三种模式，默认能力不变，但可以把远端探测从启动关键路径移出去
   - Agent 服务层、RAG 问答/入库管线、作业大模型服务和工具包导出都改成按需加载
   - 系统启动时不再提前拉起 LangGraph、`sentence_transformers`、DashScope 这类重依赖，只有用户真正进入对应能力时才加载
   - 这一轮优化把“应用启动”和“高阶 AI 能力初始化”拆开，说明系统不仅能扩功能，也能治理复杂度和冷启动成本

这类优化看起来没有“新工具”那么显眼，但它们直接决定了这套系统能不能被日常使用、被管理、被运营。

## 四、这套系统为什么有工程价值

如果只从功能数量看，我们交付的是：

<table>
  <tr>
    <td><strong>11 类</strong><br />意图识别</td>
    <td><strong>8 个</strong><br />业务工具</td>
    <td><strong>3 个</strong><br />Persona</td>
    <td><strong>3 类</strong><br />结构化卡片</td>
  </tr>
  <tr>
    <td><strong>1 套</strong><br />HITL 机制</td>
    <td><strong>1 个</strong><br />地图 MCP 底座</td>
    <td><strong>1 个</strong><br />Supervisor 最小闭环</td>
    <td><strong>36 份</strong><br />测试文档沉淀</td>
  </tr>
</table>

但如果从价值上看，我认为更重要的是下面四点。

### 4.1 它是可控的

LLM 不直接随意调工具，系统行为可追溯、可审计、可降级。

### 4.2 它是安全的

输入有中间件，高风险动作有 HITL，邮件有白名单，地图和结构化结果都有边界约束。

### 4.3 它是可运营的

有 `AgentTask`、`AgentFeedback`、监控面板、差评原因聚合、provider 分布和任务详情，系统好不好不是拍脑袋判断，而是有数据支撑。

### 4.4 它是可持续演进的

加工具不需要重写 Executor，加角色不影响意图分类，加卡片不破坏旧协议，MCP 挂了有 REST 兜底，启动路径也通过懒加载把重依赖和主应用解耦，监控面板同样开始做性能和体验收口。

## 五、现场演示建议

如果这份稿子是要配合现场汇报，我建议按下面顺序演示，观感会更顺：

1. **先讲目标，不先讲技术名词**
   - 先说“这不是聊天框，是一套 Agent 工程体系”

2. **先看用户侧，再看后台侧**
   - Agent 主对话页
   - Persona 切换
   - 结构化卡片
   - 快捷工具面板

3. **再看系统为什么可运营**
   - 反馈闭环
   - Agent 监控面板
   - provider / 差评原因 / 最近任务详情

4. **最后再讲架构价值**
   - Planner 驱动
   - BaseTool 统一工具协议
   - HITL
   - Supervisor 一期闭环
